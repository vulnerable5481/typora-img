## 1.缓存穿透



- **背景**

  ```
  用户注册的时候，需要检查用户名是否已存在，这通常要查询数据库。
  如果有恶意请求伪造大量不存在的用户，或者说有大量用户同时注册，这样都会穿透redis打到数据库。
  ```

- **解决**

  ```
  1.空缓存
  2.布隆过滤器+Redis set存储已注册用户名  (布隆过滤器+缓存)
  4.用户名#1234
  ```




## 2.缓存击穿

- **思路**
  - 1.逻辑过期   ，但是不可能所有数据都不过期，而且存储压力大，不是通用方案
  - 2.分布式锁      



- **分布式锁 + 双重判定锁**

- 思路：大量请求获取缓存中数据失败，N请求获取分布式锁， 通过分布式锁只允许一个请求访问数据库

- 问题：如果只是使用分布式锁，那么有100w个请求，只有第一个请求访问数据库更新缓存，其他请求在锁释放之后
              依然会依次获取锁，然后访问数据库加载缓存，这就导致有大量无效访问db和更新cache的操作，我们实际上只需要
             第一次即可

- 解决：

  ```
  // 伪代码如下
  if(cacheData == null){
  	Lock lock = Lock.getlock(xxx);
  	lock.lock();
  	try(){
  		if(cacheData == null){
  			dbData = mapper.selectById(userId);
  			if(dbData != null){
  				cacheData == dbData;
  			}
  		}
  	}finally{
  		lock.unlock();
  	}
  }
  ```

- 缺点：显而易见，只要缓存不过期，那么请求就永远无法更新缓存，除非你用别的方法去更新，面对追求时效性的场景就不适合

  ​          对于一些不常修改的场景非常适用，可以大大提高效率
  ​          【比如：秒杀场景】





## 3.缓存一致性



- **解决方案**
  - 1.缓存双删
  - 2.先操作数据库，再更新缓存
  - 3.先写数据库，通过binlog异步更新缓存
  - 4.加锁   



- **前三种不追求强一致性方案的差异**

  - ```
    1.如果使用到消息队列，可以使用第一种方案
    2.尽管缓存的更新是滞后的，但是大部分场景都是可以容忍这点延迟
    3.
    ```

## 1. 双重判定锁

- 第一重判定：获取锁之前，先检查数据是否合法  (比如非空)
- 第二重判定：获取锁之后，再检查数据是否合法，因为在等待锁的过程中可能数据就合法了



- 作用：双重判定锁可以在并发情况下，减少锁竞争和提高性能

## 1.ShardingSphere 





### ①核心概念



- **表**
  - **逻辑表**  ：  t_order
  - **真实表**  ： t_order_0  ~ ~ t_order_9，他们的逻辑表名为 `t_order`
  - **绑定表**  ： 分片规则一样的一组分片表
                `t_order` 表和 `t_order_item` 表，均按照 `order_id` 分片，并且使用 `order_id` 进行关联，则此两张表互为绑定表关系
                      绑定表之间的多表关联查询不会出现笛卡尔积关联，关联查询效率将大大提升
  - **广播表**：指所有的数据源中都存在的表，表结构及其数据在每个数据库中均完全一致。 适用于数据量不大且需要与海量数据的表          .              进行关联查询的场景，例如：字典表。
  - **单表**    ： 就是没有进行分片的表



- **数据节点**

  - 数据分片的最小单位，由数据源名称和真实表组成。 例：ds_0.t_order_0。
    【说白了，就是一个表分片】

  - 数据表在每个数据源的**分布方式**

    - 均匀分布： 

      ```
      db0
        ├── t_order0
        └── t_order1
      db1
        ├── t_order0
        └── t_order1
      ```

    - 自定义分布

      ```
      手动去定义数据的分布，通常都按照某些规则
      db0
        ├── t_order0
        └── t_order1
      db1
        ├── t_order2
        ├── t_order3
        └── t_order4
      ```

      driver-class-name: org.apache.shardingsphere.driver.ShardingSphereDriver
      # 指定 ShardingSphere 自定义配置文件路径地址
      url: jdbc:shardingsphere:classpath:shardingsphere-config.yaml
  ```

- ```
  # 数据源集合
  dataSources:
    # 逻辑数据源名称
    ds_0:
      # 数据源类型
      dataSourceClassName: com.zaxxer.hikari.HikariDataSource
      # 数据库驱动
      driverClassName: com.mysql.cj.jdbc.Driver
      # 数据库连接
      jdbcUrl: jdbc:mysql://127.0.0.1:3306/user_0?useUnicode=true&
      # 用户名，如果本地数据库与这个不一致，需要修改
      username: root
      # 密码，如果本地数据库与这个不一致，需要修改
      password: root
    #ds_1  这里可以创建多个数据源！
    #ds_2
    #ds_3
  
  # ShardingSphere 规则配置，包含：数据分片、数据加密、读写分离等
  rules:
    - !SHARDING
      # 需要数据分片的表集合
      tables:
        # 逻辑表名
        t_user:
          # 真实存在数据库的物理表集合
          actualDataNodes: ds_0.t_user_${0..1}
          # 分表策略
          tableStrategy:
            # 单分片键分表
            standard:
              # 自定义分片字段
              shardingColumn: id
              # 自定义分片算法名称，对应 {rules[0].shardingAlgorithms.user_table_hash_mod}
              shardingAlgorithmName: user_table_hash_mod
      # 数据分片算法定义集合
      shardingAlgorithms:
        # 自定义分片算法名称
        user_table_hash_mod:
          # 分片方式，HASH_MODE，按照 HASH 的方式对分片键进行操作，获取真实的物理表索引
          type: HASH_MOD
          props:
            # 物理表分片数量
            sharding-count: 2
  props:
    # 是否打印逻辑SQL和真实SQL，开发测试环境建议开放，生产环境建议关闭
    sql-show: true
  ```
