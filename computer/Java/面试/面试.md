## 1. 缓存



### ① 缓存穿透

- 缓存穿透就是比如说一个get请求，在redis未命中，直接打到DB，如果有人恶意攻击，就会导致DB崩溃

- ```
  方案一：缓存空数据
  	   优点：简单
  	   缺点：消耗内存，压力给到了redis；可能导致不一致的情况
  方案二：布隆过滤器
  	   根据ID查询文章 -> 布隆过滤器 -> redis -> mysql
  	   实现：底层是bitmap,去检索一个元素是否在集合中。
  			存储数据就是通过多个hash函数获取hash值，将hash值对应的位修改为1,
  			查询数据就是使用相同的hash函数获取hash值，查看hash值对应的位是否全为1，全为1说明就存在
  	   优点：底层用的是bitmap位图，所以对内存消耗就很少
  	   缺点：因为hash碰撞可能导致误判，但是精度损失很低，一般情况下都是可以接受的
  	   【注意使用布隆过滤器需要预热布隆过滤器！也就是将mysql中的数据缓存到redis，同时也缓存到布隆过滤器中！】
  ```

  方案一：互斥锁
  	   优点：强一致性
  	   缺点：性能差
  方案二： 逻辑过期
  	   优点：性能好
  	   缺点：不能保证数据绝对一致

### ③ 缓存雪崩



- 有大量的key同一时间过期，或者redis服务器宕机，导致大量请求到达数据库，带来巨大压力

- ```
  情况一：给不同的key设置随机TTL
  	   思路：既然是因为同一时间过期，那我们就给不同的key设置随机的TTL，让他们不在同一时间过期不就好了

  	   3) 给业务添加多级缓存        	 【Guava 或 Caffeine】

## 3.持久化



- **面试官：redis作为缓存，数据的持久化是怎么做的呢？**

- ```
  redis的持久化是通过RDB和AOF实现的
  首先是RDB，就是一个redis数据备份文件，也就是redis的数据快照，简单来说就是redis会把内存中的数据同步到磁盘，如果出现问题就从磁盘中读取这个备份文件用来恢复数据。
  AOF就是一个追加文件，默认是关闭的，通过配置文件开启，会将redis处理的每一个命令都追加到这个文件，可以理解为redis的命令日志文件，如果出现问题就可以通过重做aof文件里的命令，对数据进行恢复
  ```


- **面试官：RDB和AOF的区别，实际应用场景**





- 1.RDB：Redis Database BackUp file Redis数据备份文件，也被叫做Redis数据快照，简单来说就是把内存中的所有数据记录到磁盘，如果出现问题去磁盘读取，来恢复数据。

  - 1）主动备份，通过save（主线程去备份不推荐） 或者 bgsave（开一个子线程去备份）命令
  - 2）去配置文件中，比如 save 900 1  save 300 10  save 60 10000

- 2.AOF:  Append Only File 追加文件，就是说Redis处理的每一个命令都会记录在AOF文件，可以看做是Redis的命令日志文

  - 默认是关闭的，要去配置文件中开启。appendonly yes
  - 控制AOF的记录频率：appendfsync always/everysec/no  【一般我们都是使用eversync即可】

## 	4. 两个策略



**数据过期策略**

- **面试官：假如redis的key过期之后，会立即删除吗？**

- ```
  不会立即删除。
  redis的过期策略是惰性删除+定期删除，
  首先，惰性删除删除就是redis不会立即将过期的数据删除，而是当我们访问这条数据，发现他已经过期了再删除
  定期删除就是redis会定期取出部分数据，进行检测，如果是过期数据就删除
  定期删除【slow模式：定期删除和fast模式：不定期删除】
  ```

  ​	

**数据淘汰策略**

- **面试官：当redis中的内存不够用了，此时向Redis中添加新的key，那么redis是按照什么规则腾出新空间呢？**

- ```
  redis默认的数据淘汰策略，当redis空间不够了就不允许再添加新数据
  当然，我们也可以设置其他的淘汰策略。比如按照过期时间，过期时间最短的优先被淘汰；按照LRU将最近最少使用的数据淘汰；
  	完全随机淘汰；
  	平时开发过程中用的比较多的就是基于LRU的淘汰策略
  ```

- **面试官：数据库有100万条数据，redis只有20万条数据，如何保证redis留下的会是热点数据呢？**

- ```
  1.最笨的方法就是业务中修改业务逻辑，存储热点数据
  2.修改redis的数据淘汰策略，选择LRU策略，就是最近最少使用的优先被淘汰，这样剩下的就是热点数据 
  ```

分布式锁这里，我给你说一些我自己的提炼[doge]
redis setnx是最简单的一种。你也讲了 我就不说了。但有些点最好有层次的讲出来。setnx实现的分布式锁有些特性没法满足 比如不可重入 不可重试 锁过期删除的一些问题。redisson是在redis基础上也实现了分布式锁，解决了这几个问题就是redisson里面的可重入锁，比如解决不可重入用的是hash结构解决。解决不可重试基于redis的发布订阅。解决锁过期删除基于自己实现的一个看门狗机制。但是redisson这把可重入锁还有一些问题，比如主从时宕机的问题，redisson里面又可以通过有联锁啊 红锁啊解决。不过setnx基本上可以应用于分布式锁了，有一些业务上需要满足一些锁的需求的时候可以考虑更复杂的实现

2. 使用 Hash 结构实现可重入性：
在分布式环境中，简单的 SETNX 实现的锁是不可重入的，即同一个线程如果多次请求同一把锁，可能会导致死锁。为了解决这个问题，Redisson 使用了 Hash 结构来实现可重入锁。具体而言，Redisson 在获取锁时，会在 Redis 中创建一个 Hash 结构，其中包含锁的唯一标识（如线程 ID）和一个计数器。每当同一线程再次请求该锁时，计数器加一；释放锁时，计数器减一；只有当计数器为零时，锁才真正被释放。这种方式确保了锁的可重入性。
3. 基于发布/订阅机制实现可重试：
在高并发场景下，多个线程可能同时尝试获取同一把锁。如果直接采用轮询的方式重试获取锁，可能会导致大量无效请求，增加 Redis 的负担。为此，Redisson 采用了 Redis 的发布/订阅机制来实现锁的可重试功能。当一个线程尝试获取锁失败时，会订阅一个与该锁对应的频道（channel），并进入等待状态。一旦锁被释放，Redisson 会向该频道发布解锁消息，通知等待的线程重新尝试获取锁。这种方式避免了频繁的轮询操作，提高了系统的性能和效率。
4.红锁
为了解决主从一致性，redisson提供了红锁，

### ② 主从同步流程

- **面试官：redis主从是如何进行数据的同步？**

- ```
  全量同步、增量同步
  全量同步：
  		从节点向主节点请求同步数据，主节点会判断是否是第一次同步，如果是第一次同步，就会将主的版本信息给从，然后生成RDB文件，就是redis持久化的RDB和AOF，也就是一个数据快照给从，从清除本地数据，加载RDB文件获取数据。但是在生成执行RDB文件过程中，可能有新的数据变动，这些变动会以命令的形式写入到一个缓冲区也就是一个命令日志中，然后再将这个命令日志发给从，从执行里面的命令就实现了数据同步/全量同步
  增量让步：
  	    当从节点请求同步数据，主节点发现不是第一次同步数据，就会获取从的offset偏移量，根据偏移量，将命令日志offset偏移量之后的数据发给从，这样就实现了增量同步。
  ```

  - 慢查询日志记录了所有执行时间超过制定参数的所有SQL语句的日志

    long_qury_time = 2
    ```

  - 可在/var/lib/mysql/localhost-slow.log中查看

### ⑤ 索引的失效



- **面试官：什么情况下索引会失效？**

  - 索引失效的情况很多，可以说一下自己真实遇到的，而不是盲目背诵

- ```
  我们都使用name status address 联合索引来举例
  
  1.违反最左前缀法则   ⭐
  (不按顺序，比如 wehre name = 'mark' and address = '北京',中间跨域status,则只有name生效)
  （mysql 8之后的版本，即使没有完全匹配最左前缀法则，优化器会自动帮我们优化）
  2.范围查询右边的列，不能使用索引 ⭐
  (where name = 'mark' and status > 1 and address = '北京'   只有name和status生效，address失效)
  3.不要在索引列上进行运算操作
  (where substring(name,3,2))

  (where status = 1  如果status是字符串，则=1会引起类型转换导致失效)
  5.模糊查询，如果%在前，索引会失效，%在后，索引不会失效
  （why? 因为底层B+树是根据计算第一个字段的第一个字符的ASCII码来排序的）
  ```

### ① 事务的特性



- **事务是如何保证它的特性呢？**

- ```
  事务，就是一组操作作为一个整体向系统提交或撤销请求，如果任一一个操作出问题，整组操作都会回滚，即所有操作同时成功Or失败
  ```

- ```
  原子性（A）：事务是不可分割的最小操作单元，要么全部成功要么全部失败
  一致性（C）：保证了其他三个特性，一致性也就得到保证
  隔离性（I）：数据库系统提供的隔离机制，保证事务在不受外部并发操作影响的独立环境下运行
  持久性（D）：事务一旦提交或者回滚，redolog日志它对数据库中数据的修改是永久的
  ```

- ```
  回答：
  	嗯~,首先，原子性就是全部成功或者全部失败，通过undo log日志来保证，就是说失败了我就全部回滚，相对于整个事务都失败了。
  	持久性，通过redo log日志保证的，就是说当我事务提交的时候，mysql会确保redo log已经被持久化到磁盘上了，事务的实际数据更新会在之后某个时刻写入磁盘，但是redo log的写入是同步的。
  	隔离性，其实就是通过MVCC加上锁来保证的，在不同的隔离级别下，会通过不同的机制来保证它的隔离性
  	一致性，是由前面三个特性共同来保证的，如果你保证了原子性，持久性，隔离性，那么一致性也保证了
  ```




### ② 事务问题



- **面试官：并发事务带来哪些问题？**

## 3. mvcc



- **面试官：事务的隔离性是如何保证的呢？大致讲一下mvcc的底层实现**

- ```
  嗯~，事务的隔离性是由锁和MVCC实现的。
  mvcc的底层实现主要依靠三个部分，第一，表的隐藏字段，就是说我这个表这行记录是由哪个事务生成的，会通过事务ID记录；还有一个隐藏字段，应该是叫回滚指针，用来配合undo log日志 来形成一个版本链。第二，就是刚才提到的undo log版本链。 第三就是readview,
  又涉及到四个隐藏字段，比如生成该reeadview的本事务ID，会统计当前活跃的事务ID集合，最小活跃事务ID，最大活跃事务ID，也就是实际上最大的事务ID+1，就是预分配的事务ID。
  具体的流程，比如说我生成了一个readview,然后我就拿着这个readview去查看哪些数据版本对我是否可见的，它有一套匹配规则，比如根据readview里面的字段来判断，你这个事务ID是不是我自己的本事务ID，如果是的话，就说明这个数据就是本事务修改的，那当然可以访问该版本。还有就是，当前事务ID是否小于readview中的最小活跃事务ID，小于的话，就说明数据早在本事务开启之前已经提交了，那自然可以访问，对我就是可见的。再一个就是当前事务ID处于最小和最大活跃事务ID之间，并且不在活跃事务ID集合里面，说明数据已经提交了，也是可见的，可以访问。
  通过mvcc的这一套机制，事务就只能访问被允许访问的版本，不能访问的版本就相当于被隔离了,这样就实现了事务的隔离性，它就保证了一个没有锁的隔离性，按照我的理解就是mvcc不用锁而通过版本控制实现的一种隔离
  ```



- **mvcc：多版本并发控制（multi-version concurrency control）  指：维护一个数据的多个版本，使得读写操作没有冲突**

- ​    **<font color='blue'>学完mvcc，我才知道repeateble read 的真谛：我事务开始时看到的数据是啥，直到结束之前都还是它，不管其他事务如何修改，这就是事务的隔离性，通过mvcc实现，读的时候不需要锁，其他事务随便修改，不影响我这个事务的隔离性</font>**

- MVCC的实现原理
  - 通过三个隐藏字段
  - DB_TRX_ID: 最近修改事务ID，记录插入这条记录或最后一次修改该记录的事务ID
  - DB_ROLL_PTR:  回滚指针，指向这条记录的上一个版本，用于配合undo log ，指向上一个版本
  - DB_ROW_ID: 隐藏主键，如果表结构没有主键，将会生成该隐藏字段作为主键
- ![image-20250219132540801](https://zlc-typora.oss-cn-hangzhou.aliyuncs.com/img1/image-20250219132540801.png)



- **<font color=''>在repeateble read下，如何让每一个事务都只看到它想要的？通过快照，即readview</font>**
- readview中包含了四个核心字段
  - m_ids : 当前活跃的事务ID集合
  - min_trx_id : 最小活跃事务ID
  - max_trx_id：最大活跃事务ID，通常为预分配的事务ID，即最大事务ID+1
  - creator_trx_id：Readview创建者的事务ID

- **在可重复读的隔离级别下，仅在事务的第一次执行快照读的时候生成readview，后续复用该readview**
- **如果是读已提交隔离级别下，每次执行快照读都会生成一个readview，不会复用之前的。**

- **面试官：mysql这边的话，innoDB引擎用的是B+树，从你这边分析一下B+树在结构，查询时间复杂度，和B树，平衡二叉树区别**

- ```
  B+树的内部节点存储的是键值，也就是索引还有指向下一层路由的一个节点也就是一个数据页吗，它不存储实际数据，只有叶子结点才会存储实际的数据，B树的话内部节点和叶子节点都可能包含实际数据；
  B+树叶子结点会按照键值的顺序，使用双向链表连接，但是B树只是按照树的结构，不像B+树那样用链表连接。
  平衡二叉树，就是左子树的值小于根节点，右子树的值大于根节点，因为是二叉树每个节点只有两个字节点，然后左子树和右子树的高度差通常小于一个值，一般都是1。
  // 查询时间复杂度
  平衡二叉树因为节点数有限，导致树的深度一般会很深，然后B树也是
  B+树和B树都是平衡的多路查找树，所以查询复杂度都是对数级别，但是B+树的节点就指向了下一层的一个节点，在mysql也就是指向下一个数据页，在磁盘中都是以数据页的形式存储，然后每一个数据页都能开出很多节点,同时如果是叶子节点，那个节点会通过双向链表进行连接，所以层级就会变低，基本三层左右就就能满足我们的日常需求，因为层级低，虽然都是对数级别，但是B+树更适合范围查找。

  #{}的原理：（将参数绑定为预编译的占位符）

  ${}的原理： （直接拼接）
  		将参数值直接拼接到 SQL 中
  		
  使用 #：对于普通的查询条件，绝大多数情况下都应该使用 #，它能够防止 SQL 注入。
  使用 $：仅在你确定参数是安全且不能发生 SQL 注入的情况下，才使用 $。一般来说，$ 适用于动态表名、列名等无法使用 # 的场景，但即使如此，也需要谨慎使用。
  为什么#不能用在动态表名呢？因为#相当于是占位符，如果你这样写select * from #{xxx} 有#{xxx}这个表吗？直接sql就编译错误！
  					   # 占位符只是为 SQL 语句中的值提供占位，它不会修改 SQL 的结构（比如修改表名或列名）
  ```

## 7. 缓存

- 一级二级缓存

- Mybatis默认开启一级缓存

    		每个SqlSession都有一个Executor，每一个executor都有一个LocalCache,当我们进行查询时，先去LocalCache查询

## 4. 循环依赖

- **循环依赖就是循环引用，比如两个及以上的Bean互相持有对方，最终在Bean生成的时候导致死循环**

- 解决

  - Spring提供了三层缓存解决了大部分的循环依赖

    ```
    一级缓存：单例池，里面存放已经经过初始化的单例Bean
    二级缓存：缓存还没完全配置属性和初始化的Bean对象
    三级缓存：缓存的是对象工厂，用来创建对象
    比如说，我们有一个对象A和B，互相依赖对方，当我们实例化A的时候，会将A的对象工厂放到三级缓存里面。
    当配置属性的时候，发现需要B，就去实例化B，同时将B的对象工厂放到三级缓存，发现B也需要A，就从三级缓存中拿到A的对象工厂
    生成一个A的早期引用，将其注入到B，B完成初始化，就添加到一级缓存单例池里面，A从单例池拿出B进行填充，这样就实现了AB的创建，
    并且解决了循环依赖
    A-->实例化-->A放入三级缓存-->发现需要B-->B实例化-->B工厂放入三级-->发现需要A-->三级拿到A工厂生成A早期引用
    -->B完成初始化-->B添加到单例池-->A填入B-->大功告成！
    ```

    

- 特殊循环依赖：通过构造器互相持有对方

  - 解决：@Lazy注解

    ```
    public A(@Lazy B b){
    	a.b = bl
    }
    ```

## 2.JVM组成



- **<font color='red'>那么JVM的这些内存结构，是每一个线程都维护各自的吗？还是说有的共享有的私有</font>**
  - **【程序计数器，虚拟机栈，本地方法栈都是线程私有的，但是堆和方法区是共享的	】**





- **字符串常量池**
  - Jdk1.7之前，字符串常量池存在于堆里面的方法区/永久代中
  - jdk1.8之后，字符串常量池独立存在堆中，方法区则迁移到本地内存中，通过元空间的形式实现
  - String s1 = "123" String s2 = "123"  String s3 = new String("123")
  - String s1 = new String("hello").intern() 问你 s1=="hello"? **true,`intern()` 会将 `"hello"` 放入堆中的常量池，返回的是池中的引用**
  - 无非就是相当于一个缓存吗，就是你创建一个字符串实例，先去看看字符串常量池里面有没有，有就直接返回引用即可
    如果是new String()那就必须要新建



- **本地方法栈**
  - 虚拟机栈里面是java方法的栈帧；本地方法栈里面是(native)本地方法栈帧
  - 实际上，《Java虚拟机规范》对这个没有强制要求，有的java虚拟机(比如hotspot虚拟机)就直接把两者合一
  - **本地方法：就是非Java方法，通过native修饰，并且没有方法体，类似抽象接口，因为本地方法的实现是在外部，比如用C/C++**
    **等其他语言去实现的。**
    **在Java诞生的时候，编程语言是C语言的天下，本地方法就可以让很多C语言的工具融入java**
    **同时借助本地方法，也实现了java与底层系统进行交互，虽然是借助了外力，但也算是有方法了**



- **程序计数器(PC Register)**
  
  - 每一个线程都有属于自己的PC Register
  - 当线程切换的时候，PC Register 可以让当前的线程知道接下来要运行第几行字节码的代码

  - 堆中有年轻代 和 老年代

## 4. 垃圾回收



- **对象什么时候会被垃圾回收器回收？**

  - 简单来说就是：一个对象如果没有任何的引用指向它，那么这个对象现在就是垃圾，如果定位了这个垃圾，则有可能被GC回收

    - 定位垃圾的方法：引用计数法，可达性分析算法

  
    ```
    引用计数法：就是java对象的对象头里面会存储引用次数，为0，就说明这个对象是垃圾，可以被回收
    			【内存泄漏问题：出现循环引用，比如堆里面ab都是friend类，同时a.friend = b b.friend = a】
    ```
  
    ![image-20250304211704217](https://zlc-typora.oss-cn-hangzhou.aliyuncs.com/img1/image-20250304211704217.png)
  
    - ```
      所以我们更推荐使用 可达性分析算法
      实现原理：
      		就是选一些对象作为GC root对象，以此为根节点，根据其引用关系来构建一个引用链，其实和一个树有点像，然后如果沿着引用链没有找到的对象，就说明没有被引用，就会被当做垃圾。
      选哪些对象作为GC root对象：
      		1.虚拟机栈中的引用对象
      		2.方法区中类静态属性引用的对象
      		3.方法区中常量引用的对象
      		4.本地方法栈中JNI引用的对象【和系统相关，我们自己无法手动创建】
      
      ```
  
  
  
  

**类装载的执行过程**

- **JVM常见的垃圾回收算法**

  - 标记清除算法

    ```
    1.根据可达性分析算法得出的垃圾，进行标记
    2.对这些标记为可回收的内容进行垃圾回收
    
    优点：标记和清除速度较快
    缺点：碎片化严重，内存不连贯，导致不方便存储大文件，这个问题还是比较严重的
    【使用较少】
    ```

  - 标记整理算法【老年代使用这个】

    ```
    1.根据可达性分析算法得出的垃圾，进行标记
    2.移动存活的对象到连续的内存空间
    3.垃圾回收
    
    优点：解决了标记清除算法的碎片化问题
    缺点：多了一步移动，效率受到一定的影响
    ```

  - 复制算法【年轻代的使用这个】

    ```
    【空间换时间，分配有2块内存空间】
    1.根据可达性分析算法得出的垃圾，进行标记
    2.将存活对象移动到空闲的另一半内存空间
    3.清除垃圾
    
    优点：在垃圾对象多的时候，效率高；清理后，无碎片
    缺点：空间换时间，内存使用效率低
    ```

    ![image-20250304215300749](https://zlc-typora.oss-cn-hangzhou.aliyuncs.com/img1/image-20250304215300749.png)





- **说一下JVM的分代收集算法**

  - Jdk1.8中，新生代占1/3  老年代占2/3  , 然后新生代中按照8:1:1里面也进行了一次划分

  - 具体流程：
    ![image-20250305175729918](https://zlc-typora.oss-cn-hangzhou.aliyuncs.com/img1/image-20250305175729918.png)

    ```
    1.新创建的对象都会存储在伊甸园eden区
    2.当伊甸园满了，会标记伊甸园和from区的存活对象，将存活对象采用复制算法复制到to区
    3.如果伊甸园又满了，则标记伊甸园和to区的存活对象，将存活对象通过复制算法复制到from区
    4.这么来回倒腾，如果有对象熬过了很多次(最多15次)，晋升到老年代（幸存者区内存不足或者大对象都可能导致提前晋升）
    ```

  - ![image-20250305180314127](https://zlc-typora.oss-cn-hangzhou.aliyuncs.com/img1/image-20250305180314127.png)




- **垃圾回收器**
  - 串行垃圾回收器：指单线程进行垃圾回收，比较适合堆空间比较小的，适合个人电脑
  - 并行垃圾回收器：【JDK8默认使用的】虽然效率高了，但是所有线程依然要暂停，等待垃圾回收完成
  - GMS(并发)垃圾回收器：最大特点就是进行垃圾回收时，应用可以正常使用, 主要作用在老年代
  - G1垃圾回收器【JDK9以后默认使用】



- **强引用，软引用，若引用，虚引用的区别**
  - 强引用：只要所有的GC Root能找到，就不会被回收，比如我们直接new User()就是强引用
  - 软引用：当垃圾回收之后，内存还是不够用，才会回收软引用对象  new  SoftReference(user);
  - 弱引用：只要进行垃圾回收，那么就回收  new WeakReference(user);
  - 虚引用：配合引用队列使用，当垃圾回收发现一个对象有虚引用，就会在回收之前将其加入引用队列
                   可以通过虚引用管理堆外的内存，比如直接内存等不受JVM管理的内存

### ②synchronized



- **面试官: synchronized关键字的底层原理**

- ```
  synchronized底层原理，其实要提到锁升级，有三种锁。

  偏向锁:   就是同一个线程多次访问一个同步代码块，我们可以直接比较对象头里的markword字段里面的线程ID是不是自己，而不需要通过
  		 开销更大的CAS操作修改

### ⑤ AQS

- **面试官：讲解一下AQS**

- ```
  AQS是多线程的同步队列，是一种锁机制。常见的实现：ReentrantLock,Semaphone,CountDownLatch
  AQS内部维护了一个state,(private volatile int state，0无锁，1有锁),当有线程请求锁，就将state->1，如果已经是1，就代表有其他线程获取到锁了，所以就将该线程放到等待队列中，当锁被释放，state就变成0，唤醒等待队列里的线程获取锁。不过AQS既可以是公平锁，也可以是不公平锁，当有一个线程要求获取锁，同时锁已经被释放，如果是公平锁那就应该给等待队列里的线程，让刚来的的线程等待
  
  AQS和synchronized的区别：锁的竞争比较激烈的时候，synchronized是重量级的，性能差，但是AQS提供多种锁竞争方案，性能好一点
  
  AQS 的核心原理
  AQS 维护一个 state 变量（表示同步状态） 和一个 CLH 队列（FIFO 线程等待队列），线程通过 CAS 竞争 state 的值，获取锁或进入等待队列。
  
  1. state 同步状态
  state == 0 → 表示锁空闲，可被线程获取
  state > 0 → 表示锁已被占用
  state 变化通常通过 CAS（compareAndSet） 保证原子性
  2. 等待队列
  当线程获取锁失败，就会进入 AQS CLH（FIFO）队列，等待前驱节点唤醒。
  ```

  1. 当我们向hashmap put一个元素时，根据key的hash值对应的数组下标，如果这个位置已经有值了，那么就比较key是否相同
  2.存储时，如果key一致，说明put该元素就是修改这个元素，直接覆盖即可；如果key不一致，就会将其添加到这个位置对应的链表中，当然也有可能是红黑树。在jdk7之前，统一为链表，JDK8之后，如果链表长度大于等于一个阈值（8），数组长度超过一个阈值（64），就会从链表转换成红黑树，提高效率。同理，如果hashmap发生扩容，本来是红黑树但是扩容后，节点小于等于6，就会退化成链表
  3.获取数据时，直接找hash对应的下标，再进一步判断key是否相同，从而找到对应的值
  ```

  



- **面试官：HashMap的put方法的具体流程**
- 简单介绍一下，HashMap中的几个常见属性
  - **Default_INIT_CAPACITY  : **默认的初始容量
  - **Default_LOAD_FACTOR**  : 默认的加载因子
  - **HashMap.Node<K,V>[] table** :   里面有四个字段hash,key,value,next  ；这个table就是一个槽的链表/红黑树
  - **int size**  : 当前hashMap的大小
  
- ```
  put的流程：
  首先，HashMap添加一个数据，会先判断一个内部属性table是否为空，如果为空，就说明需要初始化，初始化为一个长度为16的数组，因为默认的初始容量就是16,；
  如果不为空，或者已经初始化完毕，就根据key得到对应的数组索引，找到对应的槽，判断是否为空，若为空就直接插入；如果不为空的话，就需要判断key是否存在，key不存在直接插入，若存在，则判断是否为红黑树，是红黑树的话，就不会有重复的值，直接添加；不是红黑树，那就是链表，遍历链表没有就插入，有就覆盖。jdk7之前是没有红黑树的，而且链表用的头插法,jdk8之后有了红黑树。
  链表插入数据之后，会判断链表的长度，如果>8，就转换为更高效的红黑树。
  最后，插入完还需要判断当前数组中元素的数量是否超过了阈值，阈值就是长度*加载因子，默认是0.75, 也就是16*0.75=12，假如我们超过了阈值，需要
  扩容。
  ```

  




- **面试官：HashMap的扩容机制**

- ```
  【注意扩容是在插入一条数据后去判断的】
  首先，hashmap会初始化为长度16的数组；判断是否超过阈值，阈值就是容量大小*加载因子0.75,超过了就需要进行扩容
  判断旧容量是否大于0，如果小于等于就说明需要初始化，初始化数组容量为16；
  如果大于0，就是new容量 = old容量*2，然后新建数组，遍历旧数组，如果数组每一个下标对应的槽只有一个节点就直接添加到新数组中，
  如果有多个节点，就先判断是否是红黑树，如果是红黑树就走红黑树的添加；
  是链表，就需要遍历链表，判断节点的hash&old容量==0，如果等于，就平移放在原位，newTab[j]=oldTab[j]
  如果不等于0，则需要在原来的基础上+old容量的偏移  newTab[j+oldCapacity]=oldTab[j],这种机制主要是为了解决hash碰撞，扩容后的尽量分散，而不是集中在一起。
  ```
  
  
  
- **面试官：HashMap的寻址算法**

- ```
  也就是说，HashMap底层是如何通过key得到hash，这个hash又是如何找到对应的数组索引的呢？
  首先，调用一个方法hash(key)求出来二次hash,hash(key)会return h=key.hashCode()^(h>>>16),这个怎么理解呢，其实涉及一个扰动算法，大致原理就是充分利用hash的高位，如果没有扰动算法，那么参与运算只有hash的低位，使用扰动算法就可以充分利用高位，可以很大程度上避免hash碰撞，就是不让节点集中到某个槽，而是尽可能的平均分散。
  ```

  



- **面试官：为什么HashMap的长度一定是2的n次幂？**

- ```
  1.计算数组索引的时候效率更高，如果是2的n次幂，可以使用(n-1)&hash，实际上就是取模，只是通过位运算实现，位运算底层硬件肯定快
  2.扩容时，重新计算索引效率更高：hash&oldCapacity ==0的元素留在原位置，否则新位置 = 旧位置 +oldCap
  ```

  

- **面试官：hashMap在1.7情况下的多线程死循环问题**

- ```
  在1.7中，hashmap在扩容的时候，因为链表使用的是头插法，在数据迁移的时候，有可能导致死循环
  比如说，线程1和2，线程1准备扩容，线程2介入，也开始扩容，因为是头插法会导致顺序颠倒，比如原来是AB，在线程二中就是BA，
  线程1再去扩容，进行数据迁移，会先将B插入在将A插入，会因为线程二的问题导致B的next指针指向A，A也只想B，如果遍历这个链表就会出现死循环
  ```

          boolean resultFlag = true;
          for (VerifyHanler each : handlers) {
              boolean verify = each.verify(userLoginVo);
              if (!verify) {
                  resultFlag = false;
                  break;
              }
          }
          return resultFlag;
      }

  public class DiscountStrategyFactory<T> implements CommandLineRunner {

      ApplicationContext applicationContext;
      private static final Map<String, DiscountStrategy> strategyMap = new HashMap<>();
  
      @Override
      public void run(String... args) throws Exception {
          Map<String, DiscountStrategy> map = applicationContext.getBeansOfType(DiscountStrategy.class);
          map.forEach((beanName, bean) -> {
              DiscountStrategy discountStrategy = strategyMap.get(bean.mark());
              strategyMap.put(bean.mark(),discountStrategy);
          });
      }
  
      public void chooseStrategy(String mark, T requestParam) {
          DiscountStrategy discountStrategy = strategyMap.get(mark);
          discountStrategy.discount(requestParam);
      }
  }

    Bitmap：

### ② 余量判断

- 为了超卖问题用分布式锁，但是在节假日，同一时间大量抢票，全部卡在获取分布式锁，会导致系统陷入假死状态，大量的请求堆积



- **锁升级！**
  - 1.分布式锁
  - 2.令牌桶-- > 分布式锁
  - 3.令牌桶->本地锁=>分布式锁  【这样就减少了大量请求竞争分布式锁的情况】
  - 4.优化本地锁和分布式锁的粒度， 列车ID --> 具体列车的座位类型
  - 5.间隙锁，将本地锁的范围扩大，分布式锁依然锁住列车座位类型

- **Final-Version**

  ```
  1.`引出问题`：因为考虑到节假日，或者说我自己亲身的经历，就是每个学期放假，我都得在下午五点去等候着抢票，因为我需要中转，所以经常抢到第一张票，第二张票就抢不到了，或者说抢的票可能让中转时间变长了
  2.`分布式锁`：这种情况下我们可能要解决超卖问题，我第一时间想到的就是通过分布式锁解决问题
  3.`分布式锁缺点`：但我前面也提高了这种情况下，只依靠分布式锁，一大堆用户购票请求打过来，全去抢分布式锁，可想而知，后果很严重
  4.`令牌桶优化`：因为一大堆请求竞争分布式锁，怎么解决，不让一大堆请求竞争分布式锁不就解决了吗？我去网上也搜了一下方法，类似滑动窗口法什么的，最后我选择了令牌限流，就是在redis中设计一个令牌桶，这个桶对列车余票进行映射，具体来说就是桶key就是业务前缀+列车ID+座位类型，买票不就是买一个座位，value就是该座位的余量，也就是票的数量。通过检验判断能不能买票，注意，一次购票请求可能买多张票，所以不能单纯判断余票为0就行了。lua脚本用来保证原子性，要不然不用lua脚本就还要用锁，那太笨重了。
  5.`追加问题`：使用令牌桶为什么不直接使用余票缓存？为了追求性能，追求快速判断，牺牲一定的一致性，鼓励用户自己主动操作
  6.`进一步优化`：那我既然通过令牌桶去过滤请求，但是我过滤大部分都是令牌为0之后的请求，在0之前大量的请求依然竞争分布式锁，
  我就想还能怎么优化，这时候我就想到既然我用是分布式锁，分布式锁的意思就是分布式的锁，那除了分布式锁还有什么锁？那不就是我们平时最经常使用的sycnhronized和Lock接口下的reentrantLock锁吗，不就是本地锁，那微服务架构下会有多个JVM实例，那我就可以通过本地锁来进一步过滤。
  7.`本地锁`：我们让通过令牌桶的请求先去竞争本地锁，如果你连本地锁都拿不到，那就没有资格去竞争分布式锁。

  8.`优化/降低锁粒度`：列车ID->座位类型,这样不就降低锁的粒度了吗，因为我可能一次性买多张票，票的座位可能不一样，比如两个一等票一张二等票，这样降低锁的粒度，提高性能。这就是我的第二个版本
  8.`间隙锁`，当我想起来mysql不仅仅有表锁行锁还有其他锁，比如间隙锁，那么我们是不是也可以设计一个间隙锁，比如一个列车有多个车厢，能不能在车厢类型之间建立间隙锁，这样我们就可以提高锁的粒度，为什么刚刚说降低现在又提高了呢？就是锁的粒度太细不行，这样每一个操作的开销太大了，太粗也不行，就起不到过滤的效果了，所以我认为应该选一个比较平衡的方案。就是我的本地锁，锁的是车厢，较粗的锁，提高锁的范围，分布式锁锁的是座位类型。【为什么本地锁选择锁车厢类型呢，主要考虑到一等座商务座都有各自单独的车厢,不过好像车厢类型和座位类型就是一回事，所以最后这个间隙锁是失败的版本,不过我既然想到了就还是说一下吧，不过这个间隙锁的思路沿用在了其他方面，比如你真正去扣除票的时候，要扣除A->B->C->D,>B->C->D,C->D而不只是单纯的A->D,这个间隙锁的思路可能在这里能发挥作用,不过关于间隙锁我主要就是想，并没有代码实现】
