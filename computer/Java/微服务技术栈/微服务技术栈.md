- **几个微服务框架介绍**

- 单体架构 VS 集群  VS 分布式架构

  - **单体架构：**

  ```
  单体架构：
  	1、通过打包成一个jar包，放到购买的服务器运行；
  	2、有钱再去买服务器专门部署数据库/缓存
  	3、购买一个公网ID给服务器，再买一个域名方便用户搜索
  	优点：项目模块都在一个项目，便于开发部署，操作简单
  	缺点：无法应对高并发，无法保证很高的安全性，代码更新只能停机更新
  ```

  ![image-20251007162640958](https://zlc-typora.oss-cn-hangzhou.aliyuncs.com/img1/image-20251007162640958.png)

  - **集群架构：**

  ```
  集群架构：
  	1、将项目部署到多个服务器，通过增加服务器数量来应对高并发
  	2、买一个服务器存放网关，通常是Nginx,由网关负载均衡地把请求下发给各个服务器
  	3、数据库/缓存等等也可以搭建集群
  	优点：提高了并发等能力
  	缺点：修改一个模块需要对所有服务器修改，牵一发而动全身，不方便
  		 假如有直播功能，用java开发很不方便，用C++开发直播模块，多语言团队分工合作很不方便
           代码更新虽然可以逐步更新服务，而不是让它们都下线，通过切换 nginx 配置流量实现无感更新，但是也不怎么优秀
  ```

  ![image-20251007163432801](https://zlc-typora.oss-cn-hangzhou.aliyuncs.com/img1/image-20251007163432801.png)

  - **微服务分布式架构：**	

  - ```
    微服务分布式架构：
    	1、不同模块拆分到不同服务器，如果有热点模块比如用户/商品等等比较高频，可以多部署几个，频率低的就少部署一些
    			   (这样就可以解决“单点故障”，防止因为一个模块出问题导致整个服务瘫痪)
    	2、引入注册中心：实现服务注册/发现
    	3、配置中心：注册中心一般还兼具配置中心的功能，这样就解决了哪个模块在哪个服务器的问题
    			   配置中心还有一个核心作用，假如某个模块更新，按理说需要去一个一个修改服务于中对应的模块，但是
    			   我们可以将所有的配置都交给配置中心管理，只需要更新配置中心即可实现修改所有模块版本！
    	3、远程调用：Remote Procedure Call, RPC：最常实现的形式：HTTP+JSON，解决了远程调用问题
    	4、网关：GateWay，用户依然只需要一个域名即可访问，网关可以实现负载均衡
    			网关还需要负责"请求路由"
    		    
    	
    1、什么是服务熔断？
    	问题：服务雪崩，有一条服务链，假如有百万请求从订单模块->支付模块，结果卡在了支付模块，又有其他模块例如用户模块等待
    		 订单模块的响应，因为一个模块的阻塞，导致其他模块跟着卡，最终导致多个服务器阻塞，导致服务雪崩。
        解决：通过服务熔断解决。每一次PRC如果等待时间过长就不等待了，快速返回失败，所以熔断就是快速响应失败的机制
        	 如何确定等待时间？在sentinal中配置熔断时间
    
    2、分布式事务：
    	问题：现在我们可能有多个数据库，假如支付操作涉及了支付库、订单库、用户库等，怎么保证分布式事务？
    	
    	优点：很多
    	缺点：复杂，成本高
    ```

## 5、Sentinel

### ① 基本使用

```
功能介绍：
	Sentinal是阿里巴巴的分布式流量防卫组件
	服务与服务之间的稳定性变得越来越重要，SpringCloud以流量作为切入点，使用Sentinal实现流量控制、流量路由、熔断降级等
	
定义资源：
	主流框架自动适配，所有Web接口均为资源（WebServelet、Dubbo、SpringCloud的openFeign等等）
定义规则：
	流量控制： 就是限流
	熔断降级： 防止服务雪崩，针对服务调用失败/调用时间长导致的服务雪崩问题
	系统保护： Sentinel发现当前系统整体负载太高（比如 CPU 使用率过高、平均响应时间过长等），会自动限流、降级
	热点参数： 假如商品id=100是爆款访问频率很高，那么只会对id=100的热点参数限流

使用：
	1、下载并启动sentinal控制台，可在此定义规则
	2、引入依赖
		spring-cloud-alibaba-sentinalxxxx
	3、配置yaml文件
		sentinal:transport:dashboard:localhost:8080
	4、注解式||编程式
		注解： 
			@SentinalResourse("value=xxx")
			参数：value，定义资源名，一般都是和接口url一致
			参数：blockHandler,允许我们制定兜底方法，即发生异常or触发规则后的处理
			使用：一般都是加在Service层对应的方法上面
			原理：控制台会识别到名为xxx的资源，你可以对它设置QPS限流、线程数限流、降级规则、热点参数限流等等
		编程式：
			了解即可，还是注解使用起来舒服
		案例：
        	在OrderService层
        	@Sentinal(value="createOrder")
        	public Order createOrder(Long id,Long userId,xxx){
        		// 略
        	}
		
		

工作原理：
            用户->资源
                  |
                  |-Sentinal检查
                  |
                  v
                 规则
                  |
                  v
               是否违反
                  |
                  v
          没有<------>已违反
		   |		   |	
		   |		   |	
		   v		   v
		  放行       抛出异常
		  			   |
                       V
                    兜底处理(如果有)	
```

- **snetinal控制台说明**

  ```
  Sentinel 控制台
  ├── 实时监控 —— 看数据
  ├── 簇点链路 —— 看调用结构 + 选资源
  │    ├── 流控规则 —— 控制请求速率
  │    ├── 降级规则 —— 熔断慢接口
  │    ├── 热点规则 —— 限制爆款参数
  │    ├── 系统规则 —— 整体保护
  │    └── 授权规则 —— 访问权限
  └── 集群限流 —— 分布式流控
  ```

### ③ 流控规则

```
阈值类型：
	QPS：一般都是这个
	并发线程数： 一般使用线程池的时候可能会用这个
	是否集群：  使用集群的话，比如设置1，就是单个服务模块阈值为1，集群模式就是所有服务器的某个模块加起来为1

流控模式：
	为什么有三种模式？因为一个方法可能调用别的方法形成一个调用链，管理方法需要考虑整个调用链
	如何切换？1、关闭上下文yaml文件sentinal:web-context-unify:false // 关闭上下文统一，默认情况所有资源都存在同一个上下文
			                                              sentinal_spring_web_context下被管理 
			2、在sentinal控制台切换
	1、直接：  只对当前资源生效 【默认】
	2、链路：  只对当前资源的某一个调用入口限流
    		  比如说有资源A：/user/normal；资源B：/user/vip 资源C：createOrder(即/order/createOrder)
    		  有两条链路A->C,B->C，我们可以通过对C限流，通过设置模式为链路，并配置入口资源为A,就实现了只对A调用链
    		  中的请求C资源限流，但是B不限流。【万恶的资本】
	3、关联：  如果QBS太高了，就不只是对当前资源限流，也对本调用链调用的其他资源进行限流

流控效果：
	1、快速失败 ：超过阈值就拒绝
	2、warm up： 刚开始是阈值=预设阈值的N分之一，后面慢慢加热到阈值
	3、排队等待： 超过阈值，就排队，队列里超出等待时间的就被拒绝
```

### ④ 熔断规则

```
为什么需要熔断规则？
	防止调用链中某一个资源卡住，导致整个调用链都瘫痪。
	没有熔断规则的时候，A给B发起请求，请求失败或超出响应时间就触发fallback兜底
	有熔断规则的时候， A给B发起请求，触发熔断规则，后面的请求不会发给B，这样减少了B的压力，还做到了快速响应

工作原理：
	类似电路图里的开关，准确说是断路器，如果闭合，A就可以调用B；如果打开，无法调用；
	还有一种半开状态，当熔断结束，断路器需要恢复闭合状态，先不着急，先放行一个请求，如果请求正常则说明恢复正常，否则保持打开状态

熔断策略：
	1、慢调用比例：
		超过设置的比例阈值，比如超过百分之八十的请求都超过响应时间，就触发熔断
	2、异常比例：
		easy
	3、异常数：
		统计数量，而不是百分比了
```

### ⑤ 热点规则

```
什么是热点规则？
	热点规则就是流控规则的一种，只不过精细到了参数，对热点参数进行限制。
	比如queryOrder资源中有个商品ID=100，就可以对它配置热点规则，要求id=100的商品限流
```

### ⑥ 补充

```
@Sentinal(value="xx",fallback="xx")
@Sentinal(value="xx",blockHandler="xx")

fallback与blockHandler的区别：
	1、blockHandler只能捕获Blockxx的异常
	2、fallback可以自定义捕获异常
	总结，fallback在方法本身出现异常被触发，触发任意一场
		 blockhandler在违反Sentinel定义的规则后触发，处理BlockException 及其子类异常
	
例子：
    通过Throwable就可以捕获任意异常
    public String handleFallback(String name, Throwable ex) {
    return "⚠️ 业务异常被降级：" + ex.getMessage();
    }
```

| 对比项             | `blockHandler`                                      | `fallback`                                     |
| ------------------ | --------------------------------------------------- | ---------------------------------------------- |
| **触发场景**       | Sentinel 规则触发：限流、熔断、热点参数、系统保护等 | 方法本身发生异常（业务异常、运行时异常）       |
| **处理的异常类型** | `BlockException` 及其子类                           | 任意 `Throwable`（但不包含 `BlockException`）  |
| **作用**           | 处理 **Sentinel 控制层面** 的“被拦截”请求           | 处理 **业务层面** 的异常                       |
| **参数要求**       | 参数要和原方法一致，最后再加一个 `BlockException`   | 参数要和原方法一致，最后可以加一个 `Throwable` |
| **默认返回**       | 无法返回原方法结果（被拦截）                        | 可兜底返回业务结果                             |
| **典型用途**       | 限流/降级后的“友好提示”                             | 系统内部异常的“熔断降级”返回                   |

### ② 路由

``` 
配置order与product,  要求所有/api/order/**的请求发给order;  所有/api/product/**发给product
spring:
	cloud:
		gateway:									 
			routes:									  // 路由规则(order)：
				- id: order-route                     // 每一个路由规则都有唯一标识ID
				  url: lb://order-service             // url就是目的地，lb就是启用loadbalance负载均衡
				  predicates:						  // 断言：
				  	- Path=/api/order/**			  // 请求路径匹配条件
				- id: product-route					  // 又一个路由规则(product)
				 url: lb://product-service
				 predicates:
				 	- Path=/api/product/**

1、我们可以在yaml文件配置很多路由规则，每个路由规则都可以包含id、url、predicates、filter 
2、路由的顺序，按照yaml文件汇中书写的先后顺序

工作原理：
	网关的路由规则到底是如何工作的呢？
	当请求打到网关，网关会根据断言找到对应的路由规则；执行 Filter 链；转发到目标服务（URI）
```

### ③ 断言

```
什么是断言？

有哪些断言？
	非常多，自己查阅资料。最常用的就是Path。
	每一个断言都对应一个断言工厂，底层都是借助这些工厂类实现的
自定义断言工厂：
	我们自己也可以手写断言工厂，用到再说吧	


spring:
	cloud:
		gateway:									 
			routes:									
				- id: order-route

### ④ 过滤器

```
什么是过滤器？
	  “断言”决定请求能不能进来；“过滤器”决定请求进来之后做什么加工处理。

假如我们有这么一个需求：
	之前都是手动去controller层加上的/api/xxx，万一项目开发中才临时决定这么做，如何不去修改大量代码就轻松完成呢？
	答：加入一个过滤器即可
					- id: order-route                     
				  url: lb://order-service             
				  predicates:						
				  	- Path=/api/order/**		
                  filter:	 // 这里就是重定向，将捕获的请求/api/order/** -> /**
                  	- RewritePath=/api/order/?(?<segment>.*),/$\{segment}  // 正则表达式

默认过滤器：
	我们可以设置一个默认过滤器，让所有路由规则都默认在过滤器链里面调用该过滤器，对所有路由规则都生效
	
全局过滤器：
	对所有请求（包括没有匹配路由的）都生效
	GlobalFilter 是通过 实现接口 的方式编写的全局过滤器（写在代码里，不是配置）

自定义过滤器：

```

| 类型                            | 作用范围                                                     | 配置方式                                | 说明                                     |
| ------------------------------- | ------------------------------------------------------------ | --------------------------------------- | ---------------------------------------- |
| **GatewayFilter（局部过滤器）** | 仅对匹配的某个路由生效                                       | 写在某个 `route` 下                     | 比如只对 `/api/order/**` 的请求生效      |

- **面试官： RPC和消息队列的区别**

  ```
  1、概念不同：RPC就是远程调用服务器中的方法，消息队列就是生产者去产生消息，放到队列里面，让消费者消费
  2、应用场景：RPC追求的是强一致性和关注业务逻辑的结果，消息队列则追求最终一致性，业务解耦，流量削峰。
  3、RPC就跟本地调用一样，可以立刻得到结果，成功or失败，但是MQ可能延迟消费不会立即得到结果
  4、RPC比如最简单的前后端的HTTP接口，Spring Cloud OpenFeign 就是一种RPC的实现；
     Dubbo框架就是一种轻量级的RPC框架，非常实用
  ```



- **面试官：消息队列的使用场景，有啥用**

  ```
  1、业务解耦。
     简单来说，就是只关心核心业务逻辑，其他不是那么关键的逻辑就交给下游去做。
     比如订单系统，处理订单是核心业务，订单成功给用户发短信送积分什么的，只需要发布消息通知他们即可，减少主流程的响应时间
  2、最终一致性。
  	 很多时候强一致性，分布式事务，落地太难且成本太高。
  	 最终一致性，主要是通过“记录“和”补偿“的方式，先把事情记录下来，如果失败/不确定重复执行，直到成功，通过版本号等实现幂等
  3、错峰与流量控制
  	上下游的处理能力是不同的，比如web前端可以承受千万级请求，只需搭建LVS负载均衡设备和Nginx等即可，但数据库的处理能力是有限
  	的，即使使用SSD和分库分表，单机的处理能力仍然在万级，加上成本考虑，数据库的机器数量不可能追上前端。这样的问题也同样存在于
  	系统与系统之间， 比如短信系统，但实际上用户接收短信慢个一分钟其实问题也不大。
      通过消息队列作为中间系统存储两个系统的通信内容，等下游系统有能力处理消息的时候再让它去处理，这是比较通用的方案。
  ```

  

- **面试官：常用的消息队列有哪些，它们之间的区别呢？**

  ```
  RabbitMQ,RokectMQ,Kafka
  1、定位不同。RabbitMQ是传统的MQ，RocketMQ是阿里开源的分布式消息队列，kafka是分布式日志系统
  2、可靠性，三者都支持写磁盘实现持久性，kafka和rocketmq都支持事务，但rabbitmq不支持原生事务
  3、kafka吞吐量很高，适合大数据日志，流处理
  4、rabbitmq支持push，其他两个都是pull模式
  	push就是生产者主动推送消息，实时但压力可能大，大部分情况我们用MQ都不是为了实时，故而不怎么使用push
  	pull就是消费者主动去拿消息，可控，有能力拿多少就拿多少，压力小，稍微有点延迟
  5、只有kafka不支持，其他两个都支持延迟队列和死信队列
  6、消息挤压问题，rabbitmq的设计理念就是提供一个通道，出现该问题会导致rabbitmq性能下降，可以通过增加消费者去解决
  			  其他两个的话
  			  好像还可以部署一些监控系统
  ```





- **面试官：消息挤压问题是如何解决的？**

  ```
  消息挤压问题：比如说消费太慢，或者消费端每次消费需要写入mysql,结果mysql挂了，消费就一直堆积
  1、修复消费者的问题，傻傻地等待消费者去处理，即使消费者恢复，处理也需要很多时间
     这种情况我们可以通过临时扩容的方法，修完消费慢问题，临时建立原来数倍的队列数量，写一个临时分发消息的消费者，临时夸消费者
  	数量，通过临时扩容的做法去快速消费，最后再恢复原样。
  2、如果是rabbitmq可以设置过期时间，消息直接就丢失了怎么办？或者mq已经满了，放不下了
  	这个只能临时写个程序比如刚才说到的临时扩容，先解决堆积问题，然后等夜深人静的时候手动查询丢失的这部分数据，重新发送到消息
  	队列，进行恢复
  3、消息挤压过多，MQ装不下怎么办？
  	1）刷盘
  ```

  

- **面试官：消息队列是如何保证顺序消费的，有序性**

  ```
  比如说先下单再付款，最后完成订单，这里的业务要求保证顺序

- **面试官：消息的幂等如何实现**

  1、记录。

  2、版本号控制
  ```

- **让你设计一个消息队列，该如何进行呢**

  ```
  1、首先是基于某种协议进行开发，比如AMQ，高等队列协议
  2、生产者->broker->消费者，中间需要两次rpc，可以参考dubbo框架，实现服务发现，序列化协议等等
  3、思考一些特性，比如持久化。是刷盘放到文件系统还是数据库，消息堆积怎么处理，我们可以设置一个阈值，超过阈值就丢弃部分消息腾出空间。   或者可以设置消息的过期时间，减少消息堆积的可能性；

### ② 监听信息

- **注解加在外部   -> @RabbitListener加在类**
- @RabbitHandler可以用来处理不同的数据类型，比如同一个队列里面可能有String，java类，int
  这样就可以根据数据类型 匹配不同的方法

```java
    /*
    * 写一个取消订单的监听器
    * */
    @RabbitListener(queues = "order.release.queue")
    @Service
    public class OrderCloseListener() {
        @RabbitHandler
        // 此处的Channel和Message是自动注入的，可以直接在监听者这里获取
        // Message是原始消息的详细信息
        public void listener(MemberOrder memberOrder, Channel channel, Message message) throws IOException {
            try {
                // 取消订单
                orderService.cancelMemberOrder(memberOrder);
                // 通知RabbitMQ，这个消息我处理完了，可以删除了
                // 回复之前，消息依然处于队列，只是状态被修改成了“未处理”，别人无法取出
                // false(单条确认)：确保每个订单独立处理成功后才确认
  // true(批量确认)：所有DeliveryTag小于自己的都被确认，减少网络请求，比如 1000 条日志只发送 10 次 ack，而不是 1000 次。
                channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
            } catch (Exception e) {
                // true就是消息处理失败，重新放入队列，让其他消费者处理
                // false就是消息处理失败，也直接丢弃(或者进入死信队列！)
                channel.basicReject(message.getMessageProperties().getDeliveryTag(), true);
            }
        }
    }
```

- **Message中比较常用的信息**
  - **deliveryTag**：RabbitMQ 给每条消息分配的**唯一且递增的编号**，用于**手动确认消息（Ack）**
- **Channel**
  - channel就是多路复用的通道,建立在TCP连接之上
  - 可以手动发送消息，监听队列消费消息，确认消息，拒绝消息，批量拒绝消息，声明队列，绑定队列到交换机
  - 实际应用：比如我们写了一个延迟队列/死信队列，我们从里面取出一个消息，得手动告诉它，处理成功就删除消息，反之消息按照逻辑需要，有可能还要重新放回队列
- 接收的信息也可以是一个类，因为rabbitMQ底层自动用jackson序列化，可以直接传一个类

```
@Configuration
public class RabbitMqConfig {

    // 会员订单消费Direct交换机
    @Bean
    public DirectExchange memberDirExchange() {
        return ExchangeBuilder.directExchange(QueueEnum.QUEUE_ORDER_DEAD_CANCEL.exchange).build();
    }

    // 会员订单死信队列
    @Bean
    public Queue memberDeadQueue() {
        return QueueBuilder
                .durable(QueueEnum.QUEUE_ORDER_DEAD_CANCEL.name)
                .build();
    }

    // 会员订单延迟消费队列
    @Bean
    public Queue memberTTLQueue() {
        return QueueBuilder
                // 持久化队列  【保证RabbitMq重启，队列的数据不会丢失！！】
                .durable(QueueEnum.QUEUE_TTL_ORDER_CANCEL.name)
                // 到期后要转发的交换机
                .withArgument("x-dead-letter-exchange", QueueEnum.QUEUE_ORDER_DEAD_CANCEL.exchange)
                // 到期后转发的routeKey
                .withArgument("x-dead-letter-routing-key", QueueEnum.QUEUE_ORDER_DEAD_CANCEL.routeKey)
                // 设置消息过期时间 单位ms
                .withArgument("x-message-ttl", 9000)
                .build();
    }

    // 会员订单死信队列与交换机绑定
    @Bean
    public Binding memberBinding(DirectExchange memberDirExchange, Queue memberDeadQueue) {
        return BindingBuilder.bind(memberDeadQueue).to(memberDirExchange).with(QueueEnum.QUEUE_ORDER_DEAD_CANCEL.routeKey);
    }

    // 会员订单延迟队列与交换机绑定
    @Bean
    public Binding memberTTLBinding(DirectExchange memberDirExchange, Queue memberTTLQueue) {
        return BindingBuilder.bind(memberTTLQueue).to(memberDirExchange).with(QueueEnum.QUEUE_TTL_ORDER_CANCEL.routeKey);
    }

}

- **Mysql与ES的核心区别**

  ```
  1、由于mysql的模糊查询会导致索引失效，不适合做搜索功能，ES有倒排索引，分词非常适合做搜索和分析
  2、ES中的数据是按照json格式存储的
  3、ES没有事务，mysql的innodb引擎有
  ```

- **一些概念的区别**

```
文档   ：  	一条数据就是一个文档   【ES中使用json格式】
字段   ：     JSON文档中的字段    
索引   ：     同类型文档(数据)的集合，也就是数据库中的表     【表的字段如果相同就是同一类型的文档集合】
映射   ：     索引中文档的字段约束信息，类似数据库中的表结构

mysql中的sql语句   ===>   ES中的DSL语句

```

#### ①match_all

- 全文档检索

```
一般情况都是将查询条件写在请求体，
{
	"query":{
		//全部检索
		"match_all": {} //没有条件就是查询所有
	},
	"sort": [
		{
			"account_name": "asc"  //根据account_name 升序排列
		},
		{
			"balance": "desc"     //根据 balance 降序排列
		}
	],
	"_sorce":["balance","firstName"]     //类似于select balance,firstName from xxx,规定查询数据的那些属性
	"from":5,	//分页，从下标为5的数据开始显示
	"size":10   //显示十条数据
}
```

#### ②match

- 全文档检索，对**单个字段**进行分词后匹配


```
GET /索引库名/_search
{
	"query":{
	//全文检索 会按照评分来排序,会对检索条件进行分词匹配, 这个评分就是根据倒排索引来计算出来的相关性！
	"match":{
		"address":"mill lane" //  查询地址包含mill/lane 的文档,两个字段都包含得分就高，排得靠前
	}
	}
}
```

#### ③phrase

- 全文档检索，短语匹配，**词序和距离都是评分的重要指标，匹配词必须按照顺序连续出现**。


```
{
	"query":{
	//短语检索
	"match_phrase":{  
		"address":"mill lane" //如果使用短语检索就会将mill lane当成一个完整的词来匹配
	}
	}
}
```

#### ④multi_match

- 全文档检索，允许**多个字段充**当检索条件，


```
{
	"query":{
		//多字段检索同一值
		"multi_match":{
			"query":"mill lane",//注意此处是开启分词检索
			"fields":["address","city"]  //只要address city 其中之一满足检索条件即可
		}
	}
}
```



#### ⑤ 精确查询

- **term**

  - 全文检索用match, 其他非text字段,比如boolean,int这种就使用term 精确匹配

  - ```
    {
    	"query":{
    		"term":{  
    			"account_number":20   //像这种非text的就推荐使用term
    		},
    		"match":{
    			"address":"mile lane"  //这种text之类的可分词文本 就推荐使用match
    		}
    	}
    }
    ```

    

- **range**

  - 范围检索

  - ```
    {
    	"query":{
    		"range":{  
    			"age":{
    				"gte":18,
    				"lte":30  
    			}
    		},
    		"match":{
    			"address":"mile lane"  //这种可以分词查询的字符text之类的 就推荐使用match
    		}
    	}
    }
    ```

    

#### ⑥bool复合检索

```
{
	"query":{
		"bool":{
			"must":[  //必须满足的条件
				{
					"range":{  // 18<=age<=30
						"age":{
							"gte":18,
							"lte":30  
						}
					},
					"match":{
						"address":"mill"
					}
				}
			],
			"must_not":[ //必须不满足的条件
				"match":"{
					"gender":"Male"
				}"
			],
			"should":[//应该满足的条件，满足可以加分，不满足也没有影响
				"match":{
					"firstName":"z"
				}
			]
		}
	}
}
```

{
    "query": {

            "filter": {     //如果使用filter即使满足条件也不会加分的；must,should等则都会加分
                "range": {

                        "lte": 30

                }
            }
